# 地質與座標慣例決策紀錄

本檔記錄 `GeoStructuralKit` 實作時採用的每一項慣例、採用的理由，以及**尚待確認的問題**。
程式碼與本檔不一致時，以本檔為準並修正程式碼。

---

## 1. 世界座標系：NWU（右手系）

```
X = 真北（已做磁偏角修正）
Y = 西
Z = 天頂向上
```

`north × west = up`，為右手系。對應 CoreMotion 的
`CMAttitudeReferenceFrame.xTrueNorthZVertical`。

> **App 層注意**：`xTrueNorthZVertical` 必須先啟動 CoreLocation 才會有真北參考，
> 否則 CoreMotion 會退回磁北，所有方位角都會差一個磁偏角（台灣約 −4°，
> 隨地點與年份變動）。此為 A2 階段的前置檢查項目。

## 2. ⚠️ 傾向公式：已修正原規格

原規格 A1 寫：

```
dip          = acos(n_U)
dipDirection = atan2(-n_E, -n_N)
```

**這兩行互相矛盾，會讓傾向差 180°。** 實作採用：

```
dip          = acos(n_U)
dipDirection = atan2( n_E,  n_N)
```

理由（兩個獨立驗證，皆見 `PlaneOrientationTests`）：

1. **代數**：一個向東下降的坡面為 `U = -tan(δ)·E`，即 `tan(δ)·E + U = 0`，
   其法向量正比於 `(tan δ, 0, 1)`，也就是**朝東**且朝上。傾向為 090，
   而 `atan2(n_E, n_N) = 090`，`atan2(-n_E, -n_N) = 270`。
2. **物理**：向東傾的坡面「面向東方」，其朝上法向量當然朝東上方。
   把手機平放在向東下降的岩面上，`+Z` 會朝東上方傾斜，答案必須是 090。

原公式的來源應是**下半球極點（pole）**的公式——極點朝下，其水平分量確實與傾向反向
（這也是極點在立體投影上落在傾向對側的原因）。原規格用朝上法向量算 `dip`、
卻用極點公式算 `dipDirection`，混用了兩種向量。

程式中兩者都提供且不會混淆：`upwardNormal`（朝上法向量，倒向傾向）與
`pole`（朝下極點，投影用）。

## 3. 走向：右手定則

`strike = dipDirection − 90`。沿走向方向看過去，岩面向右手邊傾斜。
另提供 `strikeAxis`（折算到 `0–180`）給不使用右手定則記錄走向的情境。

## 4. 水平面：傾向無定義

傾角小於 `0.5°` 時傾向由雜訊決定而非由岩石決定，
`isDipDirectionWellDefined == false`。UI 應只顯示傾角，
且該筆資料的傾向不得進入群集分析。

## 5. 垂直面：±180° 二義性

垂直面的兩種描述（傾向相差 180°）指的是**同一個面**，兩者都正確。

**採用**：`dip` 與 `dipDirection` **一律取自同一個向量**（朝上法向量）。
不因為垂直面而改用其他向量。

我第一版曾在近垂直時改用「實際量測到的法向量」來算傾向，
目的是避免螢幕數字在 090/270 之間跳動。**那是錯的，已修正**，原因有兩個：

1. **它犯了我批評原規格的同一個錯**——`dip` 取自翻正後的向量、
   `dipDirection` 取自未翻正的向量。對一個真實傾角 89.7°/270 的面，
   從下側（東面）量測時會回報 89.7°/090，與真實平面相差 0.6°。
2. 它破壞了「量哪一面都得到同一個位態」這個全域不變量——
   而該不變量對 10°～90° 的所有其他傾角都成立。

「跳動」其實無害：只有在平面**落在雜訊範圍內的垂直**時才會跳，
而那時兩種描述指的本來就是同一個面。真正需要處理的是顯示與儲存的確定性：

- `isDipDirectionAmbiguous` — 標記二義性
- `canonicalized` — 顯示／儲存用的確定形式（垂直面傾向取 < 180°）
- `alternativeVerticalDescription` — 給 UI 的 180° 切換鈕（非垂直面回傳 `nil`，
  因為對傾斜面翻轉傾向會變成另一個平面）

赤道平手規則：若法向量垂直分量恰為 `0.0`，`n_U < 0` 對 `0.0` 與 `-0.0` 皆為 false，
兩個面又會分歧。因此改用 `Vector3.upperHemisphereRepresentative`，
在赤道上以水平分量的固定規則決勝，兩面必得同一結果。

**待確認**：垂直面若要保留「你貼的是哪一面」這項野外資訊，
應存成獨立欄位（量測法向量的方位角），不要塞進 `dipDirection`。B 階段要不要加這個欄位？

## 6. 裝置擺放方式：以野外動作命名，不以軸命名

原本用 `DeviceAxis` 直接指定，且說明寫成「手機下緣沿線狀構造擺放」——
**那句描述是錯的**。手機的下緣作為一條線是左右走向的，平行於 `x` 軸，
不是 `y`。`−Y` 真正的意思是「手機長軸沿線，底部指向下傾端」。

改為用野外語言命名，避免這種混淆：

**外法向量的方向**：外法向量是「由岩體指向空氣」（也就是指向手持者）的方向，
因此它是**接觸面朝向的反方向**。機背朝 `−z`，所以機背貼岩面時外法向量是 `+z`；
左側面朝 `−x`，所以左側貼岩面時外法向量是 `+x`。

| `DevicePlacement`（面狀，貼哪一面） | 接觸面朝向 | 岩面外法向量 |
|---|---|---|
| `backOnFace`（預設，機背貼岩面） | `−Z` | `+Z` |
| `leftSideOnFace`（左側面貼岩面，當羅盤邊用） | `−X` | `+X` |
| `rightSideOnFace` | `+X` | `−X` |
| `bottomEdgeOnFace` | `−Y` | `+Y` |
| `topEdgeOnFace` | `+Y` | `−Y` |
| `screenOnFace`（不列入野外選單） | `+Z` | `−Z` |

> 我第一版把左／右／上／下四個寫反了（只有機背與螢幕是對的）。
> 這對**位態數值沒有影響**——`PlaneOrientation` 以軸性處理法向量，
> `+x` 與 `−x` 給出完全相同的傾角與傾向。有影響的是「量測面朝向」，
> 而那正是垂直面要記錄「你貼的是哪一面」時唯一的依據。
> 現在有物理檢核測試釘住符號：把手機立在水平面上以左側著地，
> 外法向量必須朝上。用位態斷言抓不到這個錯，因為位態是軸性的。

| `DeviceEdge`（線狀，哪一邊沿著構造線） | 沿線軸 |
|---|---|
| `leftEdge`（**預設**）/ `rightEdge` — 長邊，由機底到機頂 | `+Y` |
| `topEdge` / `bottomEdge` — 短邊，橫跨機身 | `+X` |

你說「我大多用手機左側進行量測」，所以線狀構造的預設改為 `leftEdge`。
左右長邊平行於同一軸（`y`），因此 `leftEdge` 與舊的 `−Y` 預設**是同一個軸**，
數值結果不變；線狀構造為軸性資料，手機上下顛倒也不影響。

### 量測前選擇（`MeasurementGeometry`）

擺放方式由使用者在量測前選擇，並隨每筆量測一起儲存——
事後無法回推：同一個裝置姿態，貼不同面會得到三個不同的平面，
而三個結果的傾角傾向看起來都一樣合理。沒有這個欄位的紀錄，
其中的 90° 錯誤日後無法查出。

- `DevicePlacement.fieldSelectable` = 機背、左側、右側、下緣、上緣（含右側與背面）。
  `screenOnFace` 幾何上有效但等於盲操作，不列入選單。
- `DeviceEdge.fieldSelectable` = 左長邊、右長邊、下短邊、上短邊。
- `MeasurementGeometry` 為 `Codable`，B 階段直接存進 `Measurement`。
- **只有三種選擇會改變位態**（`contactAxisPair` = x／y／z），
  因為同一軸上的兩種貼法就是同一平面的兩個面。自動偵測只需在這三者中選一個。

## 6b. 象限記法（N30°E, 45°SE）

與 dip/dipDirection 併存，不取代。`QuadrantBearing`、`CompassQuadrant`，
以及 `PlaneOrientation.quadrantDescription` / `init?(quadrantNotation:)`。

- 走向一律以北為基準寫成 `N…E` 或 `N…W`；正南北寫 `N–S`，正東西寫 `E–W`。
- 傾向以最接近的八方位字母表示，它的作用是指出平面往走向線的哪一側傾。
- **解析時，字母若落在走向線上則拒絕**（例如走向 N45E 配 NE）——
  那種紀錄本身無法判別，硬猜會憑空造出一個與真值差 90° 的傾向。
- 傾斜面若沒寫傾向字母也拒絕；只有垂直面與水平面可以省略。
- 垂直面沒有「哪一側」，所以不寫字母，讀回來是**同一個平面**而非同一串字。
- 線狀構造寫成 `45°, S30°W`（傾伏在前，與面狀相反，這是野簿慣例）。
- 解析器容忍各種寫法：`N30E`、`N30°E`、`n 30 e`、`N30E/45SE`、逗號或空白皆可。
- 顯示解析度為 0.1°，是交換格式不是儲存格式；原始值仍以 dip/dipDirection 儲存。

## 6c. 磁北原始讀數與磁偏角

`MagneticDeclination` 定義為**由真北量到磁北的角度，東偏為正**：

```
true bearing = magnetic bearing + declination
```

台灣約 −4°（偏西約 4°），且逐年變動，所以磁偏角隨量測一起存，不寫死成常數。

- `MagneticDeclination(trueHeading:magneticHeading:)` 直接由同一筆 `CLHeading`
  的兩個讀數求得。用裝置自己的這一對，而不是查表或存常數，
  才能保證磁偏角與它產生真北姿態時所用的模型一致。
- `PlaneOrientation.inMagneticNorthFrame(declination:)` /
  `.inTrueNorthFrame(declination:)`，線狀構造同。傾角／傾伏不受影響。
- B 階段的資料模型要同時存：真北位態、當時磁偏角、以及由此導出的磁北讀數。

## 7. 傾伏（plunge）與 trend

`plunge ∈ 0–90`（向下為正），`trend` 為下傾端方位角。
近垂直（plunge > 89.5°）時 trend 無定義並打旗標；
近水平時兩端等價，`isTrendAmbiguous == true`。

## 8. ARKit → NWU

`.gravityAndHeading` 為 `+x` 東、`+y` 上、`−z` 北，故：

```
north = -z_ark,  west = -x_ark,  up = y_ark
```

此映射行列式為 `+1`（真旋轉），不會鏡射。有測試驗證——若為 `−1`，
所有傾向都會左右顛倒，且不易察覺。

## 9. 平均：方位張量，不是算術平均

一次量測取樣的平均走 `T = (1/n) Σ uᵢuᵢᵀ` 的主特徵向量。

**不可用算術平均**：軸性資料的樣本可能正負相反（近垂直節理最常見），
算術平均會相消。測試中該情境的算術平均長度只剩 0.021，等同垃圾資料；
張量法不受影響，也不需要事先對齊符號。

主特徵向量的正負由解算器任意決定，因此再對齊到多數樣本的方向，
讓「你貼的是哪一面」在平均後仍然保留（垂直面才有差別）。

## 10. 角度標準差的定義

`angularStandardDeviation = sqrt(Σθᵢ² / (n−1))`，`θᵢ` 為樣本與平均軸的**軸性夾角**。

這是**單次量測取樣品質**的離散度，刻意不是 Fisher 參數。
Fisher `K` 與 `α95` 屬於 C 階段的組別統計，母體是節理組而不是一次儀器讀數，
兩者混用會讓 `α95` 小得毫無意義。

## 6d. 自動偵測貼合面：可行性

只需在三個軸中選一個（見上），不需分辨正負，因為同軸的兩種貼法給出同一位態。
可用的訊號：

| 訊號 | 能分辨什麼 | 可靠度 |
|---|---|---|
| 貼上岩面瞬間的加速度衝量 | 衝量沿接觸面法線，可分辨 x／y／z | 中。輕放無衝量；手抖會造成假訊號；沿切線滑入也偵測不到 |
| 後鏡頭／LiDAR 全暗或全距離最小 | 可靠判定「機背貼面 / 未貼」 | 高，但只限 z 軸，且耗電並需相機權限 |
| 近接感測器＋前環境光 | 可靠判定「螢幕貼面」 | 高，但只限 z 軸 |
| 重力方向 | **無法** 判定接觸面 | — |

**建議**：明確選擇 + 記住上次選擇（sticky）+ 畫面常駐顯示目前貼法，
自動偵測只當**交叉檢查**：若衝量指出的軸與選定的不同，跳警告，
絕不無聲改變設定。理由是選錯軸會產生一個差 90° 但看起來完全合理的位態，
現場從數字上無法察覺；而自動偵測本身在「輕放」與「切線滑入」時會失效。

衝量偵測器屬純運算，放在 A2（與靜止偵測共用同一段取樣資料）。

## 11. A2 取樣與品管

### 11a. 靜止偵測用「向量」標準差，不是「幅度」標準差

`StillnessDetector` 計算使用者加速度**向量**對其平均的標準差。
不能用幅度：手機被穩定地來回晃動時，加速度幅度幾乎不變、方向在轉，
幅度法會把那判為靜止。實測合成資料：等幅度擺動的幅度標準差是 `8.9e-18 g`
（會通過門檻），向量標準差是 `0.051 g`（正確地不通過）。同時檢查陀螺儀峰值，
因為手機可以在幾乎沒有線性加速度的情況下緩慢轉動。

門檻預設 `0.02 g` 與 `0.03 rad/s`（約 1.7°/s），
**這些是起點不是量測常數**，需要用真機對真岩面調一次，App 應該讓它可調。
調錯的代價是多等一下，不是精度——真正判斷一次量測能不能留的是
該次叢集自己的 `angularStandardDeviation`。

### 11b. 取樣叢集

`BurstCollector` 完全由餵進去的樣本驅動，沒有計時器也沒有並行，
所以測試可以在微秒內播完一整次量測。

- 靜止後開始，收滿 `duration`（預設 1.5 s，規格是 1–2 s）為止。
- 64 Hz、1.5 s、`minimumSamples = 10` → 從 index 9 收到 index 105，共 97 個樣本。
- 收集中若偵測到移動，**整批丟棄重來**（可關閉）。
  理由：含有手機滑動瞬間的那批資料會把滑動平均進位態裡，
  而若滑動很短，角度標準差看起來可能還是可以接受的。
- 實際到達率不足時不隱藏：`meetsRequestedSampleRate = false`，平均仍然有效。

### 11c. 磁干擾：只影響方位，不影響傾角

**這點應該寫在 UI 上**：磁干擾警告代表這筆的**方位**（傾向／走向／trend）不可信，
**傾角／傾伏仍然有效**——傾角來自重力（加速度計），磁鐵礦彎不了重力。
所以警告不等於白做一趟；日後只要補量方位就能救回這筆。

判定規則（依規格）：場強偏離 25–65 µT，或 accuracy 為 `.low`／`.uncalibrated`
→ `disturbed`。`headingAccuracy` 另加較軟的等級；**負值代表無效**
（CoreLocation 用負數表示不可用，很容易被誤當成「精度極好」）。

### 11d. 校正檢核：誤差拆成重力與磁力兩部分

`CalibrationResult` 同時給 `tiltError`（重力基準）與 `azimuthError`（磁力基準）。
拆開才有用：「總誤差 12°」無法行動；
「傾角誤差 0.3°、方位誤差 12°」等於直接說「磁力計要重新校正，
或者你正站在鋼構旁邊」。

- 水平面檢核：只能查傾角（水平面沒有方位）。
- 垂直面檢核：未給牆面朝向時只查傾角；給了就一併查方位。
- 8 字形引導：`MagnetometerCoverage` 以八分區計算覆蓋率驅動進度條。
  **權威仍然是 iOS 自己的 `accuracy`**；覆蓋率滿了但 accuracy 還是 `.low`，
  代表繼續轉，不是「完成」。

### 11e. 貼合面交叉檢查：只警告，絕不自動切換

`PlacementCrossCheck` 從接觸瞬間的衝量推斷接觸軸，**沒有任何 API 會回傳修正後的貼法**。

- 只判斷**軸**（x／y／z），不判斷正負：正負無法從衝量recover，也不需要——
  同軸兩種貼法是同一平面的兩個面，給出同一位態。
- 輕放（峰值 < 0.15 g）→ 不表態。
- 三軸能量相近（滑入、手抖，信心 < 0.6）→ 不表態。
- 有把握且與選定不同 → `disagrees = true`，跳警告。

理由：選錯軸會產生差 90° 但看起來完全合理的位態，現場從數字上無法察覺；
而這個機制在「輕放」與「切線滑入」這兩種很常見的動作下會失效。
**會在日常使用中失效的機制，不能拿來無聲地決定一個無法察覺的錯誤。**

## 12. B1 資料模型

### 12a. 分層：為什麼 SwiftData 不放在可攜核心

SwiftData 綁 Apple 平台。若把 `@Model` 放進 `OrientationCore`，整包就不能在
沒有 Xcode 的環境編譯，而**那正是現在唯一能跑測試的環境**。所以分三層：

| 模組 | 內容 | 可攜性 |
|---|---|---|
| `OrientationCore` | A1 + A2 | Foundation only |
| `FieldRecord` | B 的值型別：地質、ISRM、測線幾何、carry-forward | Foundation only |
| `FieldRecordStore` | SwiftData `@Model` | 整檔包在 `#if canImport(SwiftData)` |

`FieldRecordStore` 在 Linux 上編譯成空目標而不是編譯失敗，所以 `swift test`
對可測的部分仍然可用。

### 12b. 每個 `@Model` 存「一個 blob + 幾個查詢欄」

每個 `@Model` 把它的值型別（`MeasurementRecord` 等）當成單一 Codable 屬性存，
**那個屬性是唯一的真實來源**。另外複製少數欄位成普通 column，
純粹是因為 `#Predicate` 無法伸進編碼後的 blob。

替代做法是一個欄位一個 column —— 三十個欄位散成三十條宣告，
要靠人工跟值型別保持同步，而失敗模式是某個欄位靜靜地沒被存下來。
現在往返是結構上無損的，而重複的 column 只在 `apply(_:)` 一個地方寫入。

### 12c. ⚠️ ISRM 級距界線請你核對

所有界線都寫成 enum 上的數值範圍，並有測試逐一釘住，**改一處即可**。
`python3 tools/reference_check.py` 會把整張表印出來。
**這些是我依標準表格回想出來的，請對照你手邊的 ISRM 版本確認** ——
界線錯了的話，所有依它分類的紀錄都錯，而專案裡沒有其他測試會發現。

界線一律**半開區間 `[下界, 上界)`**：間距恰為 60 mm 算 `close`（60–200），
不算 `veryClose`（20–60）。ISRM 的表寫成「20–60 mm」沒說界線歸哪邊，
所以這是一個選擇，而且一致地套用到每一個尺度。

| 尺度 | 級距 |
|---|---|
| 間距 (mm) | <20 極密 / 20–60 很密 / 60–200 密 / 200–600 中等 / 600–2000 寬 / 2000–6000 很寬 / ≥6000 極寬 |
| 延續性 (m) | <1 很低 / 1–3 低 / 3–10 中 / 10–20 高 / ≥20 很高 |
| 張開度 (mm) | <0.1 / 0.1–0.25 / 0.25–0.5 / 0.5–2.5 / 2.5–10 / 10–100 / 100–1000 / ≥1000 |
| 風化 | W1 新鮮 … W6 殘餘土 |
| 含水 | I 乾而緊閉 / II 乾但有流動痕跡 / III 潮 / IV 滲水 / V 連續流 |
| 端點 | x 延伸出露頭 / r 終止於完整岩石 / d 終止於另一不連續面 |
| 粗糙度 | I–IX：stepped（I–III）、undulating（IV–VI）、planar（VII–IX），各為 rough→smooth→slickensided |

**張開度的重疊：兩個都保留，但不等價。** 原表把「wide, > 10 mm」放在 gapped
群組末尾，又把「very wide, 1–10 cm」放在 open 群組開頭，所以 50 mm 有兩個合法名稱。

- `ApertureClass.wide` 存在，**可以儲存**，所以照原表寫的舊野簿值能原樣存進來，
  不會被悄悄改寫。
- 但它**不在 `derivable` 裡**，`init(millimetres:)` 永不產生它 ——
  量到 50 mm 一律得到 `veryWide`，確定且可重現。

若沒有這個區分，分類結果會取決於 enum case 的宣告順序。

**JRC 仍接受 0–20**（規格寫 1–20）。Barton 的圖版下限是 0 —— 完全平滑的平面 ——
所以 0 有物理意義，而把 20 以外的輸入拒絕掉比夾到 20 更安全（夾過的 25 看起來
會像「量到圖版上最粗糙的面」）。**這是三個項目裡唯一我沒有改的**，要改成下限 1
講一句就好。

### 含水狀態：ISRM 兩張表都在，而且刻意不可混淆

| 評等 | 無充填 `UnfilledSeepageRating` | 有充填 `FilledSeepageRating` |
|---|---|---|
| I | 緊閉乾燥，不可能有水流 | 充填物高度壓密且乾燥，透水性極低 |
| II | 乾燥但有過去流動痕跡（染色） | 充填物潮濕，無自由水 |
| III | 潮濕，無自由水 | 充填物濕，偶有滴水 |
| IV | 滲水，偶有滴落 | 充填物有淘洗跡象，連續流（記流量） |
| V | 連續流（記流量） | 充填物局部被淘空，沿通道大量流動（記流量與壓力） |

**同一個評等號在兩張表意思不同** —— III 在一張是「潮濕無自由水」，
在另一張是「充填物濕、偶有滴水」。所以設計上**不是**「一個 enum + 一個布林旗標」，
也不是裸的數字：`SeepageObservation` 是 `.unfilled(…)` 或 `.filled(…)`，
存進去的值自己說明它來自哪張表。否則存下來的 `III` 事後無法判斷用的是哪張。

另加一致性檢查 `seepageScaleMismatch()`：充填物記為 `clean` 卻用了有充填表、
或反之，都會回報。**值得檢查而不是信任** —— 兩張表共用評等號，
用錯表的讀數看起來完全合法，卻落在離真值三格的地方。

### 12c-2. 不連續面類型：15 種標準 + `other(String)`

新增：席狀節理、斷層帶、剪裂帶、片理、張裂隙、縫合線、不整合面、侵入接觸面、流面。
加上原有的節理、層面、斷層、葉理、劈理、脈，共 15 種標準類型。

- `other(String)` 承接長尾，**標籤原樣保留**，不會把所有特殊構造併成一個桶。
- 編碼為 `storageKey` 純字串（`other:擠壓帶`），不用 enum 關聯值的合成表示法 ——
  因為這個值會出現在資料庫欄位與匯出檔裡，`{"joint":{}}` 既醜又脆弱。
- `commonCases` 只有 5 種（節理/層面/斷層/葉理/脈）給野外選單第一頁。
  **這不是在判斷哪種岩石重要，是在判斷小螢幕上的一隻冷手** ——
  第一頁每多一列，每一次量測都變慢，包括那些只會用到 `joint` 的量測。

**帶狀類型有厚度**：`faultZone` 與 `shearZone` 的 `isZone == true`。
斷層帶若當成單一平面量，會丟掉工程師第一個問的量。
`zoneThicknessMetres` 是它的位置，並且**與充填物厚度分開** ——
剪裂帶是數公尺的分布式應變，充填物是單一裂隙裡的數公釐，加在一起沒有意義。
`zoneThicknessIssue(for:)` 雙向檢查：帶狀類型沒厚度（紀錄不完整）、
平面類型有厚度（可能是類型選錯，或充填物填到錯欄位）。

### 12c-3. 取樣方式：6 種，其中一種的修正方法留給 C

| `SurveyGeometry` | 偏壓修正 |
|---|---|
| `scanline`（測線） | `terzaghi` |
| `borehole`（鑽孔／岩心） | `terzaghi` |
| `window`（測窗） | `terzaghi` |
| `traceMap`（平面露頭的 photogrammetry trace map） | `terzaghi` |
| `surfaceModel`（3D 點雲／網格，表面朝向多方向） | `areaWeightedSurface` |
| `selective`（選擇性挑選） | `unavailable` |

- `borehole` 幾何上就是測線，但分開一個 case，因為**出處**在事後讀資料時重要：
  鑽孔取到測線碰不到的岩石，而它的方位偏壓通常強得多 ——
  垂直孔對水平節理幾乎是盲的。
- `traceMap` 幾何上就是測窗，修正方式完全相同；分開是為了紀錄 trace 怎麼來的，
  因為 photogrammetry trace map 與手繪測窗能解析的細節不同。
### 12c-4. 取樣偏壓：一條關係式統管全部

所有可修正的幾何共用同一條關係：

> **視頻率 ∝ sin(不連續面與取樣元件的夾角)**，所以偏壓權重是它的倒數。

| 取樣元件 | 效率 |
|---|---|
| **線** `s`（測線、鑽孔） | `\|pole · s\|` ← Terzaghi 原始關係 |
| **面** `m`（測窗、trace map） | `\|pole × m\|` |

**這兩者對極點的依賴方向相反。** 平行於露頭面的節理在面上完全不留 trace
（需要最大的修正），而沿該面法向量的測線卻能完美取到它。
所以把露頭面的法向量餵給測線公式，會讓修正完全顛倒。

> ⚠️ **B1 第一版我就是這樣寫錯的。** 原本 `samplingDirection` 對測窗回傳面法向量，
> 文件還寫「權重 = 1/cos(極點與此方向夾角)」——
> 那會讓最難取到的節理得到權重 1，最容易取到的得到無限大。
>
> 現在改成 `SamplingElement` 列舉（`.line(LineOrientation)` / `.plane(PlaneOrientation)`），
> 讓兩種公式在型別上不可能互相誤用，並有一個測試直接斷言「誤用會顛倒」。
> 測窗公式另外用 trace 間距數值驗證過：間距平行平面相距 S 時，
> 在露頭面上的 trace 間距為 `S / sin(兩面夾角)`，四組位態誤差 < 1e-9。

### 12c-5. 推薦：3D 表面模型用「面積加權的同一條公式」

**不要為 3D 另找一套方法。測窗公式本身就能推廣。**

把露頭表面當成一組有面積 `Aᵢ`、朝向 `mᵢ` 的 facet。每個 facet 就是一片小測窗，
所以某一位態能被看見的比例是各 facet 效率的面積加權平均：

```
E(n) = Σ Aᵢ · |n × mᵢ|  /  Σ Aᵢ
```

推薦它的理由，依重要性排序：

1. **不是新理論，是同一條關係式加總。** 沒有額外假設、沒有要挑的文獻參數。
2. **單一 facet 時必須與測窗公式完全相同** —— 這是個可測的強性質。
   實測 19 × 24 組位態，最大差異 `1.1e-16`。
3. **面積會自動約掉**，所以結果取決於朝向分布而不是模型的尺度大小。
4. **成本與網格大小無關**：facet 可以先併進幾百個朝向分箱再加總。
5. 退化行為正確：單一朝向的露頭會還原成那個測窗。

已實作為 `SurveyGeometry.samplingEfficiency(for:)`，三種幾何共用一個函式。

#### 但權重本身刻意**不**在這裡

取倒數需要上限（規格建議 5–10），而**上限會把低效率的組別靜靜地少報**。
所以：

- 這一層只給 `E(n) ∈ 0...1` 的原始幾何量。
- C 階段負責決定上限、以及「效率低到什麼程度就該回報為『未取樣』而不是『已修正』」。

**盲區是這件事的要害。** 單一朝向的露頭對平行於它的節理組是全盲的：

| 節理位態 | 單一面露頭（85/120） | 三朝向露頭 |
|---|---|---|
| 85/120（平行） | **0.0000** | 0.3850 |
| 80/125 | 0.1226 | 0.4613 |
| 45/090 | 0.7408 | 0.8072 |
| 05/000 | 0.9991 | 0.8127 |

效率 0 的那一組，無論上限設多少都會被截斷成一個有限權重 ——
看起來像「修正過了」，其實是「根本沒看到」。
所以 C 必須同時回報效率本身與是否觸及上限，
而不是只給一個截斷後的數字。這跟專案其他地方一致：**打旗標，不編造**。

## 13. B2 野外紀錄流程

### 13a. 分層：UI 盡量薄

UI 在這台機器上完全無法執行或截圖。所以所有**會出錯的決定**都搬到 `FieldSession`
（Foundation only，由注入的事件驅動），`FieldUI` 只剩擺位。

| 模組 | 內容 | 可測 |
|---|---|---|
| `FieldSession` | 狀態機、觸發語意、確認閘門、尺寸常數 | ✅ 完全可測 |
| `FieldUI` | SwiftUI 畫面、外接鍵接線 | ❌ 未執行過 |

### 13b. 一顆按鍵在每個狀態的意思

只有一顆按鍵，而且可能是看不到的藍牙鍵，所以同一個按壓必須在每個狀態都是
「明顯正確」的那件事：

| 狀態 | 按一下代表 |
|---|---|
| 閒置、剛儲存 | 開始量測 |
| 靜止偵測中、取樣中 | **取消** —— 不是「再開一次」 |
| 複查中、無旗標 | 接受並儲存 |
| 複查中、有旗標 | 拒絕，並用別的方式告知 |

**第二列是最重要的。** 鍵在口袋或手套裡時，無法分辨刻意的第二次按壓與不小心的誤觸；
若第二次按壓是「再開一次」，第一筆會被無聲丟棄。
**取消可以復原，遺失的量測不行。**

### 13c. 旗標只收回「盲操作」這條路，不阻止儲存

**警告永不阻止儲存。** 地質師站在露頭前，程式不在。
如果他看過被擾動的方位後決定留下，那是他的判斷；
一個拒絕儲存的 App 只會讓那筆資料被寫到紙上。

警告做的是**收回不看螢幕的那條路**。戴手套用藍牙鍵時螢幕可能全程沒被看過，
所以第二次按壓必須預設安全 —— 而它只在「沒有東西需要看」時才安全。
有旗標的量測仍然存得下來，只是需要刻意看一眼。

| 警告 | 收回盲操作？ | 理由 |
|---|---|---|
| 磁干擾 | ✅ | 方位不可信 |
| 貼合面不一致 | ✅ | 可能差 90° |
| 取樣分散過大 | ✅ | 可能手滑 |
| 取樣率不足 | ❌ | 平均仍然有效，只是樣本少 |
| 無定位 | ❌ | 位態本身有效，峽谷裡可能一直都沒有 |
| 描述欄位矛盾 | ✅ | 繼承來的描述可能不適用 |

`autoConfirmWhenClean` 預設關閉。它是最快的迴圈（貼上去就有紀錄），
也是唯一能讓整個專案塞滿沒人看過的資料的設定。
即使開啟，**有旗標時仍然會停下來**。

### 13d. 兩個設計細節，各自修正了一個真問題

**衝量視窗在閒置時就要滾動。** 自然的動作順序是「先把手機貼上岩面，再按鍵」——
所以接觸衝量發生在按鍵**之前**。我第一版在按鍵時才開始記錄動作樣本，
那會讓衝量視窗裡完全沒有它存在的理由，貼合面交叉檢查永遠不會有意見。
現在閒置時也持續滾動（上限 64 個樣本，約 1 秒），
儲存或丟棄後清空 —— 新的量測需要新的證據，
**錯的意見遠比沒有意見糟糕**，而空視窗產生的正是「沒有意見」。

**環境是在叢集結束時快照，不是在確認時。** 地質師可能走開才按確認；
沿露頭三十公尺外的定位屬於另一條節理。有測試專門斷言這件事。

### 13e. 手套模式的數字

| | 標準 | 手套 |
|---|---|---|
| 最小可點邊長 | 44 pt（Apple 公布的裸指下限）| 68 pt |
| 主要按鍵高度 | 64 pt | 110 pt |
| 控件間距 | 12 pt | 24 pt |
| 文字倍率 | 1.0 | 1.25 |
| 單手拇指可及範圍 | 底部 50% | 底部 45% |

**間距跟尺寸一樣重要** —— 兩顆大按鈕之間沒有空隙，對手套來說仍然是一個模糊區域。

手套那一欄是起點，需要真的戴著手套在野外試一次。
這類數字錯了不是正確性問題，是「冷手點錯東西」問題，
而這台機器上沒有任何測試能發現它。

主要按鍵必須落在拇指可及的底部帶內。螢幕上方的控件是雙手控件，
在邊坡上另一手拿著地質錘時，等於不會被使用。

## 14. C1 投影與等值線

### 14a. 兩種投影，各有其用

| | 保留什麼 | 用在哪 |
|---|---|---|
| `equalArea`（Schmidt / Lambert 等面積） | **面積** | **一律用來算密度** |
| `equalAngle`（Wulff / 等角） | 角度（圓仍是圓） | 幾何作圖、手繪習慣 |

兩者都是**下半球**投影，圓心為垂直、原週圓為水平，且 θ=0 → r=0、θ=90 → r=1。

- 等面積：`r = √2 · sin(θ/2)`
- 等角：`r = tan(θ/2)`

**密度一律在等面積網格上計算，不論顯示用哪一種。** 原因：等面積投影裡
均勻的方格網格就是半球的等面積均勻取樣，σ 尺度才站得住。
等角網格會把中心擠密，從它算出來的每一個統計量都偏了。顯示時重新投影節點，
**不要重新建網格**。

### 14b. 資料點與曲線需要不同的摺疊方式

`project(axis:)` 用赤道平手規則摺疊 —— 軸與其反向落在同一點，這是**資料點**要的確定性。

但同一個規則用在**曲線**上是斷點：大圓的端點正好落在地平面上的走向線，
兩個端點會被摺到同一點，跡線的頭尾被綁在一起；
水平面的整條跡線都在地平面上，會崩成半個原週圓畫兩次。

所以另有 `projectCurvePoint`，**只摺疊嚴格在地平面以上的部分**。
實測對照（平面 50/120，走向 30°）：

| | +走向端點 | −走向端點 |
|---|---|---|
| 資料摺法 | 210° | 210° ← 綁在一起 |
| 曲線摺法 | 30° | 210° ✓ |

### 14c. 小圓跨越地平面會產生三段，必須接回兩段

錐面掃完 360° 時，含 φ=0 的那段弧會被「掃描起點」切成兩半。
球面上兩個圓最多相交兩次，所以最多三段；首尾同狀態時接回去（去掉共用點）。

| 軸傾伏 / 錐角 | 段數 |
|---|---|
| 70° / 10°（全在下半球）| 1 |
| 3° / 15°（跨越地平面）| 2 |
| 0° / 20° | 2 |

兩段**不可以連起來** —— 連起來會在投影圖上畫一條沒有意義的線。
上半球的部分被摺到對足點，出現在網的另一側，那是幾何事實不是缺陷。

### 14d. Kamb 計數圓：兩條獨立推導互為檢核

Kamb 的想法是讓資料自己決定平滑程度。對 `N` 個軸、計數圓佔半球面積比例 `a`，
均勻分佈下期望計數 `E = Na`、標準差 `σ = √(Na(1−a))`。令 `E = kσ`：

```
Na = k²(1 − a)   ⟹   a = k² / (N + k²)   ⟹   （k=3）a = 9/(N+9)
```

角半徑由球冠面積得到：`a = 1 − cos ρ`。

**第二條路徑**：等面積投影保面積，所以計數圓的投影半徑佔原週圓比例是
`√a = 3/√(N+9)` —— 文獻常引的形式。兩條路徑互不知情，
**一致到 5.5e-17**，有測試釘住。

| N | a | ρ | E | σ | E/σ |
|---|---|---|---|---|---|
| 50 | 0.1525 | 32.06° | 7.63 | 2.54 | 3.000 |
| 200 | 0.0431 | 16.88° | 8.61 | 2.87 | 3.000 |
| 1000 | 0.0089 | 7.66° | 8.92 | 2.97 | 3.000 |

樣本越大、計數圓越小 —— 這正是「讓資料決定平滑程度」的意思。

### 14e. ⚠️ modified Kamb 的權重函數我不確定

規格要求含 modified Kamb。我實作的權重是 `(1 − (φ/ρ)²)²`，
**但published 的權重可能不同，請對照你的文獻確認。**

不過真正讓 σ 尺度有意義的不是權重的形狀，而是**圍繞它的重新歸一化**：

換了權重，`E` 與 `σ` 都會變，為硬邊計數圓算的 σ 尺度就失效了。
所以程式對**任何**權重都重算矩並重解半徑，使 `E = kσ` 仍然成立。
算式靠一個事實：**均勻分佈的軸，與任一固定方向的軸性夾角 φ 密度恰為 `sin φ`**
（在 0–90°，積分正好為 1）。所以每個樣本的

```
E/N = ∫ w sin φ dφ          Var/N = ∫ w² sin φ dφ − (∫ w sin φ dφ)²
```

硬邊時這兩式還原成 `a` 與 `a(1−a)`，也就是上面的解析式 —— 有測試對照。

平滑權重解出的 ρ 比硬邊**更寬**（N=200：22.66° vs 16.88°），
因為邊緣權重遞減，要更寬才能累積同樣的統計量。

### 14g. 密度會飽和 —— 別把截頂的峰值當成集中度

**節理組比計數圓更緊時，密度就封頂在 `N/σ`。** N=200 時 ρ=16.88°，於是：

| 散佈 | 中心密度 |
|---|---|
| 8° | 69.67σ ← 飽和 |
| 12° | 69.67σ ← 飽和 |
| 15° | 69.67σ ← 飽和 |
| 20° | 49.46σ |

## 14f. 水平線狀構造的投影：以記錄的 trend 為準

第一次跑 CI（297 個測試）時抓到的三個錯誤之一，記在這裡因為它是**慣例決策**，
不只是程式錯誤。

`plunge = 0` 的線狀構造，它的兩端在軸性意義上完全等價：trend 000 與 trend 180
是同一條線。問題是畫在赤平投影上要畫哪一端。

- `project(axis:)` 用**赤道平局規則**（tie-break）：`u` 與 `−u` 必須落在同一點，
  否則一個垂直節理從兩面量到的兩個法向量會畫成兩個點。這對**極點**是對的。
- `project(line:)` 現在改為**只折疊嚴格在地平線以上的向量**，也就是水平線保持原樣。

原因：地質師在野簿寫下 trend 000，投影圖就不能把點畫在 180。這兩個需求
（極點的決定性 vs 記錄的忠實性）是真的互斥的——對同一個垂直節理的兩個法向量
套用「忠實於記錄」會畫出兩個點。所以用兩個入口函式解決，不是折衷。

`LineOrientation.isTrendAmbiguous` 仍然負責標示「這條線的兩端本來可以互換」。

**附帶發現的赤道接縫（equator seam）**：平局規則以 `x` 的正負決定，而 `x` 在
方位 090° 與 270° 恰好為零。`cos(90°)` 在浮點下是 `6.1e-17` 而不是 0，所以
方位 089.9999° 與 090.0001° 這兩個相差 0.0002° 的極點，會畫在圓周上相距約 180°
的兩點。這不是可以修掉的 bug——圓周 360° 要表示 180° 的不同軸向，任何代表元
選法都有一道接縫。近垂直節理本來就由 `isDipDirectionAmbiguous` 標示。
加一個 epsilon 只會把接縫搬到 `|x| < 1e-12`，不會消滅它，所以沒有加。
